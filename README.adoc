= tx_engine (Rust Coding Test)

A toy payments engine. It reads transactions from a CSV, keeps a balance per client, applies disputes and chargebacks, and prints the final state of every account as CSV.

== Update after 5 years / AI usage

The original implementation (2021) was written without any AI assistance. Five years later I came back to it and reworked it, and the commits from 2026 are that rework.

The rework was done with an AI coding agent (Claude Code) in an interactive session. I drove it: I chose the designs, pushed back on the proposals I disagreed with, and reverted several changes that did not earn their keep. The agent read the code, ran the benchmarks and the sample inputs, and wrote the commit messages from the staged diff, as one-liners in Simplified Technical English. Every decision in this repository is mine, and I am happy to walk through any of them.

== Running it

----
cargo run -- transactions.csv > accounts.csv
cargo test
----

The summary goes to stdout and every rejected row goes to stderr, so redirecting stdout gives a clean CSV. The _./assets_ directory holds the sample inputs, each paired with the output it has to produce, and `cargo test` runs all of them through the engine and compares.

== How a dispute works

I read the engine as an exchange that takes card payments: a deposit is a payment in, a withdrawal is a payout out. A dispute is then not something the client raises. It is the card issuer pulling a deposit back, after a stolen card for example. The task asks for exactly that kind of reading:
____
When in doubt on how to interpret a requirement, try to make assumptions that make sense for a bank.
____

That one picture settles the rules the task leaves open. Only a deposit can be disputed, because a withdrawal was requested and authenticated by the client and no third party can reverse it. A dispute row carries no amount, because the issuer points at the original transaction instead of restating the sum. A chargeback locks the account, because the deposit was probably fraudulent, and nothing unlocks it, because that call belongs to a human.

A dispute on its own locks nothing. It moves the disputed amount from available to held and leaves the rest of the balance usable while the issuer decides. A balance can end up negative when the funds left before the chargeback arrived, which is the loss the exchange takes. _./assets/test_010.csv_ records that case.

== Decisions

- A malformed row is rejected, never repaired. *Example:* a dispute with the wrong client ID, or with an amount field.
- A locked account takes no deposit and no withdrawal, but a dispute, a resolve and a chargeback still go through.
- A dispute is allowed even when the client has nothing available, so balances can go negative.
- Amounts print with the scale the arithmetic produced them in, with no padding and no rounding. *Example:* `held` shows `0` for an account that was never disputed, and `0.0` once a dispute moved an amount with one decimal place.
- The summary is sorted by client ID, so two runs over the same input give identical bytes. A library caller that needs no order can ask for `SummaryOrder::Unsorted` and skip the sort.

== Errors

There is no `unsafe` code, and no `unwrap`, `expect` or `panic!` outside the benchmarks.

- Bad arguments: usage on stderr, exit code 2, the same as `ls`, `grep` or `sort`.
- A file that cannot be read, or output that cannot be written: message on stderr, exit code 1.
- A row the engine refuses: message on stderr, the row is skipped, and the number of skipped rows is printed at the end. The run still succeeds, because one bad row says nothing about the rest of the file.

== Design notes

Every handler reads first and writes second, with a comment marking the two halves, so a rejected transaction leaves the storage exactly as it was and the engine needs no rollback. Among the writes either none can fail or only the first one can, so a failure never stops halfway. `Account::hold` and `Account::release` compute both amounts before they assign either. A deposit is the one exception: it may create the account it pays into before it adds to it, which is safe because a new account starts at zero.

Every amount uses checked arithmetic, so an overflow is an error and not a panic. A deposit checks the total as well as the available amount. Without that check a deposit could fill available while a dispute held the same sum, and the account would be stuck: its summary would not print, and its dispute could only be charged back, never resolved.

The state of a dispute lives on the stored deposit it refers to, not in a map of its own. A dispute without a transaction, and a dispute of a withdrawal, therefore have no representation.

== What is not here

A few hours is enough for a careful prototype, not for everything. The vectors in _./assets_ cover the engine from input to output, but there is no unit test per function and no performance work beyond the benchmarks. Several parts of the task are open to interpretation, and *How a dispute works* explains the reading I settled on.
